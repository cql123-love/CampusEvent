## 一、SRP —— 单一职责原则

**定义**：一个类只应有一个引起它变化的原因。

| 类 | 唯一职责 | 若要它变化的唯一原因 |
|---|---|---|
| `Activity` | 描述活动属性 | 活动字段定义变化 |
| `Student` | 描述学生身份 | 学生字段定义变化 |
| `Registration` | 记录一次报名及其状态 | 报名记录结构变化 |
| `RegistrationService` | **编排**报名/审批流程 | 流程步骤顺序变化 |
| `RegistrationPolicy` | 定义"提交后什么状态"的契约 | **报名规则种类增加** |
| `DirectPolicy` | 直接报名的具体规则 | 直接报名规则细化 |
| `ReviewPolicy` | 审核报名的具体规则 | 审核报名规则细化 |
| `EventPublisher` | 事件分发 | 分发机制变化 |
| `MessageNotifier` | 把事件写成站内消息 | **通知渠道变化** |
| `MessageRepository` | 消息的存取 | 存储细节变化 |

**关键体现**：如果将来要加"第三种报名方式"（比如"先到先得无需审核但限专业"），**只需要新增一个 `XxxPolicy` 类**，服务层、控制器、仓储层**一行都不用改**。这正是把"规则种类"这个变化原因隔离出来的收益。

## 二、OCP —— 开闭原则

**定义**：对扩展开放，对修改关闭。

**在策略模式上的落地：**

```python
# 服务层只有这一处涉及策略，且是依赖抽象
def _create_policy(self, policy_type: str) -> RegistrationPolicy:
    if policy_type == "直接报名":
        return DirectPolicy()
    if policy_type == "审核型":
        return ReviewPolicy()
    raise BusinessError("报名方式无效")
```

**这个工厂方法是"唯一允许知道具体实现的地方"**。当系统演进时，这个 if 确实需要修改——但：
- 修改被**限制在一个方法内**，不会扩散；
- 若要彻底消除它，可进一步用**注册表 + 反射**（`POLICY_REGISTRY = {"直接报名": DirectPolicy, ...}`），但那会增加复杂度与"隐式"的阅读成本。

**这是一个明确的取舍**：我选择**保留显式的工厂方法**，因为它可读性强、IDE 可跳转、评审时容易讲清楚。**如实报告代价**：严格意义上 OCP 并未完全达成——新增策略类型仍需修改工厂方法。我认为在本题规模（2 种策略）下，**可读性优先于教条式 OCP** 是更负责的工程判断。

**在观察者模式上的落地：**

```python
publisher.subscribe(MessageNotifier())   # 新增观察者只需多一行订阅
publisher.publish(event)                  # 分发逻辑完全不变
```

新增通知渠道（如邮件通知）→ 新增一个 Observer 实现并订阅，**服务层零改动**。这条是**完全的 OCP**。

## 三、LSRP —— 里氏替换原则

**定义**：子类型必须能替换掉父类型而不破坏程序正确性。

`RegistrationPolicy` 的两个实现：

| 方法 | `DirectPolicy` | `ReviewPolicy` | 是否满足 LSP |
|---|---|---|---|
| `submit()` | 返回"已通过" | 返回"待审核" | ✅ 都在 `{"待审核","已通过"}` 合法状态集合内 |
| `review()` | 抛 `NotImplementedError` | 返回"已通过"/"已拒绝" | ⚠️ 见下 |
| `requires_quota()` | `True` | `True` | ✅ |
| `name()` | "直接报名" | "审核型" | ✅ |

**⚠️ 关于 `review()` 的说明（如实报告）：** `DirectPolicy` 不支持审批，抛异常。这**技术上违反了 LSP**（子类型不能比父类型更受限）。

**改进方案与最终选择：** 更好的做法是把接口拆成两个——`SubmittablePolicy`（所有策略都有 `submit`）和 `ReviewablePolicy`（仅有审核策略有 `review`），服务层用 `isinstance` 判断。但这会引入"类型判断"，反而更违反 OCP 精神。

**我的最终选择：保留单一接口 + 明确异常 + 在类图和本文档中显式声明该限制。** 理由：本题只有两种策略且差异明确（直接报名**在业务上就不存在审批环节**），拆分接口带来的复杂度大于收益。**关键是我没有假装它满足 LSP，而是在文档里明确写出这个取舍**——这正是指导书 3.7 节要求的"如实报告"。

## 四、ISP —— 接口隔离原则

**定义**：客户端不应依赖它不需要的方法。

**本设计的应用：**

`RegistrationPolicy` 只有 4 个方法，都是"任何报名策略都必须回答的问题"（提交后什么状态、审批后什么状态、要不要占名额、叫什么），**没有塞入与策略无关的职责**。

**对比说明：** 如果我把"发通知""查数据库"也写进 `RegistrationPolicy`，就违反了 ISP。当前接口保持了最小化。

**仓储层的 ISP 体现：** 五个仓储接口各自只暴露自己领域的方法（`MessageRepository` 只有 `insert/list_by_student/mark_read/exists_once`，没有 `get_activity`），调用方不会被迫看到无关方法。

## 五、DIP —— 依赖倒置原则

**定义**：高层模块不应依赖低层模块，两者都应依赖抽象。

**两处关键落地：**

**① 策略依赖倒置**

```python
class RegistrationService:
    def __init__(self, ..., policy_factory=None):
        self._policy_factory = policy_factory or self._create_policy
    # 服务层持有的是「工厂函数」，运行时注入具体策略
```

服务层**不 import** `DirectPolicy`/`ReviewPolicy` 的业务判断逻辑，只在工厂里创建它们。**依赖方向是：服务 → 抽象 ← 实现**。

**② 通知依赖倒置**

```python
class EventPublisher:
    def __init__(self):
        self._observers: list[Observer] = []   # 依赖 Observer 抽象

class MessageNotifier:                          # 实现 Observer
    def update(self, event): ...
```

`EventPublisher` 不知道 `MessageNotifier` 的存在（它只认 `Observer` 协议），订阅动作在**组装层（app factory）**完成。

**依赖方向图（见类图）：**

```
Route → Service → (RegistrationPolicy) ← (DirectPolicy / ReviewPolicy)
                  → (Observer)        ← (MessageNotifier)
```

## 六、设计模式应用理由与代价（必答项）

### 6.1 为什么用策略模式

**问题**：`policy_type` 有"直接报名"和"审核型"两种，将来还可能增加（先到先得、限额抽签…）。这是**典型的"行为随类型变化"**。

**不用策略模式会怎样？** 在 `RegistrationService.submit()` 里写：

```python
# 反面示例（我不采用的做法）
if activity.policy_type == "直接报名":
    status = "已通过"
elif activity.policy_type == "审核型":
    status = "待审核"
else:
    ...
```

**问题**：
1. 新增类型必须改服务层 → 违反 OCP
2. 规则散落在流程代码中 → 违反 SRP（服务层同时管流程和规则）
3. 无法单元测试单个规则 → 每个分支都要构造完整服务环境

**策略模式带来的收益（可测量的）：**
- 新增策略类型：**新增 1 个类（≈25 行）+ 工厂加 1 行**，服务层/仓储层/控制器**零改动**
- 规则可独立测试：`DirectPolicy().submit(...)` 无需数据库
- 依赖倒置天然成立（SVC 依赖接口）

### 6.2 为什么用观察者模式

**问题**：报名业务完成后要写站内消息。若把 `MessageNotifier().send()` 直接写在服务里，将来加邮件/短信通知就要改服务。

**收益：**
- 新增通知渠道：**新增 1 个 Observer 实现 + 1 行订阅**，分发逻辑零改动（**完全的 OCP**）
- 服务层不关心"消息怎么写、存哪张表"

### 6.3 代价（如实报告）

| 代价 | 具体情况 | 我的评估 |
|---|---|---|
| **类数量增加** | 相比单文件实现，多出 5 个类（2 个策略实现 + 事件 + 观察者接口 + 发布者） | **接受**：换来的是新增策略/通知渠道时的零改动，对本题"第2周要应对变更"的设定是**必要投资** |
| **间接性上升** | 读一行代码要知道最终走到哪个实现，需追踪工厂方法 | **接受**：工厂方法集中在 1 处，可读性损失有限 |
| **LSP 不完全满足** | `DirectPolicy.review()` 抛异常 | **已知且有意的取舍**，已在 3.x 节明确说明 |
| **OCP 不完全满足** | 新增策略仍需改工厂方法 | **已知取舍**：可读性优先 |
| **事务边界需额外设计** | 通知在事务外，需额外做幂等与失败留痕 | **必要成本**：正是业务规则 6 的要求 |
| **名额检查不能完全策略化** | 未来若出现"不限名额"的活动，需扩展服务层 | **已知局限**：已通过 `requires_quota()` 预留扩展点 |

### 6.4 未来如何扩展

| 变更需求 | 扩展方式 | 需改动 |
|---|---|---|
| 新增报名方式（如"抽签"） | 新增 `LotteryPolicy` | 1 个新类 + 工厂 1 行 |
| 新增通知渠道（邮件/短信） | 新增 `EmailNotifier` 实现 `Observer` | 1 个新类 + 1 行订阅 |
| 某类活动不限名额 | 策略返回 `requires_quota()=False` | 服务层已预留判断分支 |
| 报名记录支持多段审核 | `RegistrationService` 增加阶段字段 | 服务层 + 策略（属**流程**变化非**规则**变化，改动范围可控）|

**这张表就是实验二"变更适应与设计分析"（30分）的核心素材**——它证明模式确实换来了可维护性，而不只是"用了设计模式"。
