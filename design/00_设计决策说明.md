## 一、设计任务 A：识别职责与绘制类图

### 1.1 领域对象识别过程

从指导书附录 B 的业务规则出发，我按"数据归属"和"行为归属"两条线索划分对象：

| 线索 | 提问 | 结论 |
|---|---|---|
| 数据归属 | 哪些数据有独立的生命周期？ | Activity、Student、Registration、Message 各自独立持久化 → 四个实体 |
| 行为归属 | 哪些行为只对一类对象有意义？ | "报名" 只对 报名记录 有意义 → Registration 是实体，不是 Activity 的属性 |
| 变化性 | 哪些规则将来会变？ | **报名规则**（直接/审核）和**通知方式**（站内信）会变 → 抽成两个策略 |
| 无状态性 | 哪些类是纯逻辑、无需持久化？ | RegistrationPolicy 实现类、NotificationService 的分发部分 |

### 1.2 职责划分

| 类 | 职责（只做这些） | 明确**不**负责 |
|---|---|---|
| `Activity` | 描述活动本身：标题、时间、地点、容量、报名方式 | 不管谁报了名、不管通知 |
| `Student` | 描述学生身份 | 不管报名规则 |
| `Registration` | 记录"某学生对某活动的一次报名"及其状态流转 | 不做名额判断、不发通知 |
| `RegistrationService` | **编排**整个报名/审批流程，调用策略与通知 | 不实现具体规则细节 |
| `RegistrationPolicy`（抽象） | 定义报名规则的统一接口 | 不关心数据库、不发通知 |
| `DirectPolicy` / `ReviewPolicy` | 各自实现"提交后该是什么状态" | 不关心通知、不管名额统计 |
| `NotificationService` | 把事件转成站内消息并落库 | 不改业务状态 |

### 1.3 依赖方向

**依赖一律指向抽象，不指向具体实现**：

```
Route（表现层）
   ↓ 依赖
RegistrationService（应用层）
   ↓ 依赖（抽象）           ↓ 依赖（抽象）
RegistrationPolicy      EventPublisher / Observer
   ↑ 实现                    ↑ 实现
DirectPolicy          MessageNotifier
ReviewPolicy
```

- `RegistrationService` 只依赖 `RegistrationPolicy` **接口**，运行时注入具体实现（工厂方法 `create_policy(policy_type)`）。
- **没有** `if policy_type == "直接": ... else: ...` 这类硬编码分支散落在服务里。
- `NotificationService` 实现观察者接口，`RegistrationService` 只负责 `publisher.publish(event)`，**不直接 new MessageNotifier**。

## 二、设计任务 B：策略模式表达变化的报名规则

### 2.1 抽象定义

```python
class RegistrationPolicy(ABC):
    @abstractmethod
    def submit(self, activity, student) -> str:
        """提交报名后返回的初始状态：'待审核' 或 '已通过'"""

    @abstractmethod
    def review(self, activity, registration, approved) -> str:
        """管理员审批后返回的最终状态"""
```

| 策略 | 提交后 | 审批后 |
|---|---|---|
| `DirectPolicy`（直接报名） | 直接 `已通过` | 无需审批（方法不适用，抛 `NotImplementedError` 或返回原状态） |
| `ReviewPolicy`（审核型） | `待审核` | `已通过` / `已拒绝` |

### 2.2 ⚠️ 关键设计决策：名额检查属于**公共规则**，不是策略责任

**这是指导书明确要求解释的点，我的结论是：名额检查放在 `RegistrationService`（公共规则），不放进策略。**

**理由：**

1. **业务规则 3 的原文是"名额统计按'已通过'报名计算"** —— 这条规则对**所有**活动类型都成立，与"直接报名还是审核报名"无关。如果放进策略，就要在两个实现里写两遍一模一样的代码，违反 DRY。
2. **两种策略的差别只在"提交后进入什么状态"，不在"能不能报"**。一个审核型活动同样会满员、一个直接报名活动同样要查重复报名。把公共校验塞进策略，会让策略接口承担不属于它的职责（SRP 违背）。
3. **策略模式的收益是"隔离变化"**。变化的只有"审批与否"这一条轴。如果把名额检查也塞进策略，等于把不变化的东西也绑到了变化的东西上，反而削弱了策略模式的收益。

**代价（如实报告）：** 名额检查在服务层，意味着**将来若出现一种"不受名额限制"的活动**（比如无限名额的公开讲座），需要改动服务层而非只加一个策略实现。这是一个**真实的可扩展性代价**，我在 3.7 的可维护性分析中量化了它。

**折中：** 我把名额检查抽成服务层的一个**独立可测方法** `check_quota()`，而不是散落在流程代码里。这样未来若真需要"豁免名额"的策略，可以给策略接口加一个 `requires_quota` 属性，服务层据此决定是否调用——**在不破坏现有结构的前提下**留出了扩展点。

### 2.3 公共规则在服务层的落点

`RegistrationService.submit()` 的执行顺序（每一步都是"公共规则"）：

```
1. 校验活动存在
2. 校验活动未开始（业务规则 5）
3. 校验学生无重复有效报名（业务规则 4）
4. 校验名额（业务规则 3）—— 直接报名时立即占用名额
5. ★ 调用 policy.submit() 决定初始状态（这里才用策略）
6. 保存 Registration
7. 发布事件 → 观察者写站内通知
```

**注意第 5 步的顺序**：策略只在"决定状态"这一步介入，前后全是公共规则。这正是策略模式的正确用法。

## 三、设计任务 C：解耦报名业务与通知机制

### 3.1 解耦方式：观察者模式 + 事件对象

采用**观察者模式**（指导书允许"观察者模式或等价的事件分发结构"，明确说**无须引入消息队列**）。

```python
class EventPublisher:
    def __init__(self): self._observers = []
    def subscribe(self, observer): self._observers.append(observer)
    def publish(self, event):
        for obs in self._observers:
            obs.update(event)      # 观察者异常不向上抛
```

**事件对象** `RegistrationEvent`：携带 `student_id`、`activity_id`、`content`、`event_type`（报名成功/待审核/通过/拒绝/取消）。

**观察者** `MessageNotifier`：实现 `update(event)`，把事件翻译成站内消息写库。

### 3.2 ⚠️ 关键设计决策：通知失败不影响报名事务

**指导书要求解释"通知失败是否影响报名事务"，我的结论是：不影响。**

**理由：**

1. **业务规则 6 的原文**："通知失败应留痕，但不得导致已经合法提交的报名记录无声消失"。这直接给出了答案——报名记录必须落库，通知是次要的。
2. **业务价值上，报名是学生主动发起的、对学生更重要的事**；站内通知只是一个提醒渠道。如果通知失败导致报名回滚，学生会丢失报名结果，而系统里其实"什么都没发生"，这对用户是不可接受的。
3. **反向论证**：如果通知失败导致报名回滚，那么"报名 + 通知"就成为一个分布式事务，在没有消息队列的前提下只能靠补偿实现，复杂度远高于收益。指导书也明确说了不用消息队列。

**具体实现（事务边界）：**

```
RegistrationService.submit()
  ├─ BEGIN
  ├─ 校验 + 保存 Registration   ← 核心事务
  ├─ COMMIT                        ← 到此报名已持久化
  └─ publisher.publish(event)      ← 事务外！通知失败不影响上面的记录
```

**通知失败的留痕方式：** `MessageNotifier.update()` 内部用 `try/except` 捕获异常，把失败信息写入 `notification_log` 表（含 event 类型、目标学生、失败原因、时间），**不向上抛**。同时在观察者循环里也做了隔离——**一个观察者失败不影响其他观察者**。

**如何避免重复通知：** `MessageNotifier` 在写消息前检查"该 student_id + activity_id + event_type 在最近一次状态变更后是否已通知过"。实现上采用**幂等键**：`messages` 表上建唯一索引 `(student_id, activity_id, event_type, related_registration_id)`，重复写入时捕获 `IntegrityError` 静默跳过。这样即使事件被重复发布，也不会产生重复消息。

**这样设计的一个已知局限（如实报告）：** 通知失败时，学生**不会收到**这条提醒（消息没写成功），只能靠管理员在通知日志里看到。若要保证"最终送达"，需要引入重试队列或定时补偿任务 —— 但那超出了指导书限定的范围（"无须引入消息队列"），所以我选择**明确记录失败**而非**假装成功**。

## 六、待评审确认的设计取舍汇总

| # | 取舍点 | 我的选择 | 备选方案 | 选择理由 |
|---|---|---|---|---|
| 1 | 名额检查位置 | **服务层公共规则** | 放进各策略实现 | 规则 3 对所有活动类型成立；避免 DRY 违背；策略只隔离真正变化的"审批与否" |
| 2 | 通知失败是否回滚报名 | **不回滚，失败留痕** | 回滚保证强一致 | 规则 6 明确要求；避免分布式事务复杂度 |
| 3 | 管理员删除有报名的活动 | **拒绝删除并提示** | 软删除 + 列表过滤 | 软删除需额外处理所有查询的过滤条件，易漏；答辩解释成本更低 |
| 4 | 防重复通知 | **幂等键 + 唯一索引** | 内存集合去重 | 内存去重在重启/多进程下失效；数据库唯一索引是唯一可靠手段 |
| 5 | 是否引入消息队列 | **不引入** | 引入 MQ | 指导书明确"无须引入消息队列"；超出限定范围属项目膨胀 |

> **第 1、2 项是指导书点名要求解释的**，答辩时应重点展开。
> **第 3、4、5 项体现了"模式有代价"的如实报告**，符合 3.7 节"如模式使结构变复杂，也应如实报告"的要求。
