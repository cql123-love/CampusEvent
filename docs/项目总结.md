## 第一页：目标、范围与真实性边界

本实验的目标不是只做一个可以打开的网页，而是用需求分析、职责划分、设计模式、版本管理和回归测试证明系统能够应对变化。CampusEvent 面向管理员和学生：前者发布校园活动并审批申请，后者浏览、报名、取消及接收结果。初版包含直接报名、审核报名和站内消息；教师变更增加年级限定直接报名与模拟邮件通知。

项目使用 Python、Flask、SQLite，允许固定演示账号，不实现真实注册、支付、短信或复杂权限。所有演示身份、活动和邮件收件地址都用于教学。模拟邮件不访问 SMTP，也不引入付费第三方服务。公网初版部署在腾讯云，云资源的试用期限及费用须由账号持有人确认，不能据“本次未花钱”承诺永久免费。

本次先保存教师需求的影响分析和设计图，再在变更分支添加测试、实现和证据。原标签保留，不删除项目重建。报告区分本地测试、浏览器验证和生产验收，不用本机截图替代公网写入与重启证明。变更版源码和材料已准备，生产升级与真实同学签名仍需完成。

初版历史材料中存在“已评审”和“全系统零修改”等过强措辞。本次没有编造签名或回填不存在的人工过程，而是在当前文档标明实际状态。学生需要审阅这些分析，理解其理由后用于答辩，不能把 AI 的说明直接当作本人已验证的事实。

## 第二页：初始需求与领域建模

初始业务的关键对象是 Student、Activity、Registration 和 Message。学生与活动通过报名记录关联，报名有独立标识、状态和时间，因此不能只保存为活动中的学生名单。取消和拒绝记录需要追溯；同一人再次申请时创建新记录，不能覆盖旧结果。

名额只按已通过人数计算，待审核暂不占用。直接报名在容量足够时通过，审核报名先进入待审核，管理员批准时重新查容量。有效报名包括待审核与已通过，同一学生同一活动不能有两条有效记录。活动开始后关闭新增报名，学生只能取消自己的可取消记录。

职责划分采用分层结构：Flask 路由解析表单并渲染；应用服务编排业务；策略负责变化的报名规则；仓储读写 SQLite；事件发布与观察者隔离通知。统计通过仓储聚合，由 ActivityService 返回，不在 Activity 中缓存剩余人数，避免审批、取消时出现重复维护。

初版 UML、报名时序、审批时序与用例说明均保留。核对实际代码时发现原图把统计方法放进了实体，还把活动查询画成报名仓储查询。变更图修正这些差异，同时保持原图作为历史证据。原图存在不准确内容，不能通过修改旧标签掩盖。

验收以 C1～C10 为核心，覆盖活动创建、直接通过、重复拒绝、容量限制、审核申请、批准、拒绝、满额审批、取消及重启保留。完整映射见初始 SRS 分析和需求验收表。

## 第三页：策略与观察者的设计选择

报名方式是主要变化点。RegistrationPolicy 定义提交、审批和配额相关接口；DirectPolicy 与 ReviewPolicy 分别返回已通过或待审核。名额、时间和重复有效报名是公共约束，继续由 RegistrationService 编排，不能在每个策略中复制相同查询。

教师 CR-01 只新增一种限定类型，因此 GradeLimitedDirectPolicy 继承直接策略，在提交时检查年级 2、3。通过后复用原直接行为；普通直接与审核策略不检查年级。这比引入通用规则引擎更符合本题规模。代价是工厂、学生字段、数据库约束、后台校验和页面都必须适配，不是只新增一类就完成。

通知采用 EventPublisher 和 Observer 协议。报名保存并提交后才发布事件，AppContainer 订阅站内消息和邮件两个观察者。RegistrationService 不认识 MockEmailSender，不根据渠道分支。这样邮件故障不会回滚已完成的报名，站内渠道也不会因为新增邮件而消失。

SOLID 的收益是变化职责更清晰、策略可独立测试、发送器可故障注入；代价是类数、间接调用和装配工作增加。当前仓储没有再建立一套抽象接口，直接策略仍不支持审批，不能宣称完全满足所有原则。禁止待审核期间切换报名方式解决了具体异常路径，但没有通过文字把接口局限变成优点。

最终 AST 对照显示报名核心类保持一致，活动服务需要修改。模块级导入、异常迁移和其他层仍有真实变化，报告同时列出，避免用局部指标包装全系统。

## 第四页：变更实现、迁移与并发

CR-01 为 Student 增加 1～4 的整数年级，实体和数据库均校验。为兼容旧构造，grade 放在原创建时间字段之后，缺省为 1。标准演示账号明确映射到四个年级；其他旧账号不从学号猜测年级，也不默认获得限定资格。

CR-02 新增 MockEmail、MockEmailRepository、MockEmailSender、EmailNotifier。邮件只针对已通过和已拒绝事件，待审核与取消的原站内消息保留。模拟收件人为学生 ID 加保留的 invalid 域，不收集真实邮箱。记录包含收件人、主题、正文、状态、时间和错误。

模拟发送的唯一可观察副作用是数据库记录。按报名 ID 和事件类型建立唯一键，重复投递及重启后投递不会新增记录；失败邮件与错误日志在同一独立事务保存。失败不自动重试，也不承诺真实 SMTP 的恰好一次投递。进程在报名提交后、事件发布前崩溃仍可能漏通知，这是未引入事务发件箱的已知边界。

旧库不能靠 CREATE TABLE IF NOT EXISTS 自动升级。迁移在显式事务中增加年级、重建活动类型 CHECK、保存原 ID 和历史、创建邮件表与约束，并检查外键和完整性。故障时回滚，未知未来版本拒绝降级。线上工具先备份，脚本停止写入后迁移，不删库重建。

并发请求可能同时通过前置校验，因此有效报名唯一索引、容量触发器和条件更新负责写入最终约束。它们是数据保护，不把服务中的先查后写误称为原子事务。

## 第五页：测试、真实失败与修复

从 baseline-v1 解包的原始版本重新运行得到 22 项通过；变更版共 77 项 pytest 通过，无失败、错误或跳过。原 C1～C10 及原边界断言保留，新增 CR、迁移、故障、重复事件、并发报名及审批测试。原 Web 流程 12 场景通过。机器日志和 JUnit XML 已入库，可以重新执行生成。

浏览器使用本机 Edge 实际创建限定活动，以年级 1 报名得到拒绝，以年级 2 报名成功，并验证消息页的两个渠道。桌面和手机共 8 项布局检查无整页溢出，无页面脚本错误。截图来自一次性本地库，不是生产证据。

过程并非始终通过：新增测试在旧代码上因缺少新策略出现收集错误；实现首轮有一个断言错误，要求拒绝正文包含与状态完全相同的词，忽略原文“被拒绝”的等价表达。修正为核对事件类型、主题及对应站内正文一致，未改变原业务语义。

真实代码缺陷包括日期只比较到天、非法日期可保存、有历史报名时删除触发外键错误、待审核时切换方式导致审批异常。已分别修复并补回归。另修复页面把方法对象当布尔值阻止再次报名，以及 E2E 第三学生未创建造成的弱验证。

本地测试通过不能替代服务器升级。生产仍须执行备份、升级、双渠道和重启保留验收；同学签名也不能由自动化完成。最终回归表明确列出这些未被替代的环节。

## 第六页：维护性指标与证据

类统计范围为 src 下顶层类，通过 AST 对照初版与当前代码。新增 5 类，类总数由 22 到 27。BusinessError 只是迁移模块，不重复计数。两个核心业务服务中仅 ActivityService 修改；RegistrationService 类 AST 未变，服务文件并非整体未改。

最终回归失败数为 0。早期收集错误和一项断言失败保留记录，不将最终成功描述为从未失败。本次由用户发起的实现回合为 1；此前全部历史交互没有完整计数，不能补造总轮次。功能实施从 14:43:35 到实现提交 15:03:23，为 19 分 48 秒，不含前期部署与设计，也不含之后报告和演示材料收尾。

版本证据是初版 baseline-v1、设计稿 995b351、影响分析和红测试 66bb167、实现提交 489e8cf，以及最终 change-v2。变更分支从初版建立，再合入已有部署准备提交，没有覆盖旧标签。教师可以查看真实差异，而不是只阅读“用了设计模式”的结论。

模式确实减少了报名主流程中因新类型和新渠道引起的修改，但并未消除持久化与界面变更。数据库保护也增加了维护成本，状态或容量规则变化时要同步测试。性能、可靠消息投递和真实认证没有在本实验中作出超范围承诺。

本次没有维护另一套无模式项目来制造对照。结论来自同一系统两个真实版本和可复现测试，指标口径完整记录在可维护性对照中，不能只选择对架构有利的数字。

## 第七页：交付、部署与反思

仓库包含源码、依赖、运行说明、初始需求分析、用例、初版及变更版 UML、报名和审批时序、设计原则、影响分析、测试表、机器证据、AI 日志、总结和答辩 PPT。报告同时提供 Markdown、Word 与七页 PDF，图保留 PlantUML、SVG 和 PNG。

AI 承担需求整理、代码实现、测试生成、图表渲染和材料编排；学生仍须理解边界、检查关键判断、让真实同学评审并完成生产验收。不能把 AI 自动写出的“学生判断”当作未发生的人工行为。历史日志本次未逐项追溯验证，新记录只描述可确认操作。

运行先安装 requirements、生成演示数据再启动。已有腾讯云升级使用 change-v2 和 deploy/upgrade.sh，先测试再停服务、备份、迁移、重启。失败时保留备份并查日志，不强制覆盖数据库，不公开 production.env。提交网页答案仍只填写仓库和公网地址两行。

主要经验是：新增规则不仅是一个条件，兼容性涉及旧学生、旧活动 CHECK、原通知、历史报名、界面与测试；第二，通知隔离不是吞异常，需要可观察失败和持久去重；第三，现有测试通过也可能漏掉日期、删除和并发边界，需要针对风险补测。

当前剩余事项是生产服务器变更版升级、真实云端业务写入和重启验收、同学签名，以及学生本人阅读并确认报告。未完成这些事项前，不能宣称指导书所有环节已经结束。真实局限比未经验证的“全部完成”更有助于答辩。
