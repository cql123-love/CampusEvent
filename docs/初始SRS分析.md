# 初始需求分析（补充整理）

依据：实验指导书第三章与附录 B。日期：2026-11-26。此文件是对既有初版需求和实现的补充归纳，不冒称在初次编码前已经存在。原始设计提交与 `baseline-v1` 可追溯；评审签名仍须实际完成。

## 范围与角色

CampusEvent 为校园活动报名与管理教学 Web 应用。管理员创建、编辑和删除活动，审批申请并查看统计；学生浏览、筛选、报名、取消及阅读通知。允许固定演示账号，不要求真实用户注册、付费服务、短信、支付、复杂权限或移动 App。

技术边界为 Python + Flask + SQLite。数据库必须持久化；云部署须有公网 URL，不能用本机地址替代提交地址。公开演示不适合录入真实个人信息。

## 领域与职责

| 对象 | 数据与职责 |
|---|---|
| Student | 学生 ID、姓名；初版无年级 |
| Activity | 活动 ID、名称、分类、时间、地点、正整数容量、报名方式 |
| Registration | 学生与活动的一次申请，含状态、创建与更新时间 |
| Message | 学生接收的消息，含内容、时间、已读状态与关联报名事件 |
| RegistrationService | 编排公共规则、策略选择、保存与事件发布 |
| ActivityService | 活动维护与实时统计 |

报名记录独立保存，取消和拒绝后保留历史。名额由已通过人数实时计算，不能将待审核人数当作占用。

## 状态转换

- 直接提交：创建已通过记录；审核提交：创建待审核记录。
- 待审核可批准或拒绝；批准需剩余名额，失败后保持待审核。
- 待审核或已通过可由本人取消；拒绝和取消为历史，不阻止后续新申请。
- 同一学生、同一活动最多一条待审核或已通过记录。
- 活动开始后不允许新增报名。
- 通知失败不能使已经提交的报名消失，失败须留痕。
- 对已有报名历史的活动，本项目采用拒绝删除，而非软删除。

## 设计与风险

报名方式是策略变化点，通知渠道是观察者变化点。公共时间、重复和容量规则不是某个具体策略私有。通知在报名提交后执行，避免渠道失败影响业务。

初版测试不等于所有边界均正确：日期粒度、历史删除、切换报名方式及并发竞争的缺口在变更阶段补测并修复，见回归报告。新教师需求单不反向改写为初版要求。
