## 1. 需求与保持不变的行为

| 变更 | 新增要求 | 保持不变 |
|---|---|---|
| CR-01 | `Student.grade` 为整数 1～4；新增“年级限定直接报名”，仅年级 2、3 可报名，其余明确拒绝 | 普通直接报名与审核报名不受年级限制；时间、名额、重复有效报名约束继续生效 |
| CR-02 | 保留站内消息，增加 Mock 邮件；记录收件人、主题、内容、状态、时间；失败留痕；同一事件不重复发送 | 报名及审批状态不被邮件故障回滚；原有站内消息不被替换 |

邮件覆盖“已通过”和“已拒绝”：直接报名通过、限定年级报名通过、审核通过、审核拒绝。待审核、已取消不新增邮件，但保留既有站内通知。教师未要求真实 SMTP、真实邮箱、付费邮件平台或消息队列。

## 3. 设计选择与代价

### 3.1 独立年级策略

采用 `GradeLimitedDirectPolicy(DirectPolicy)`。本次只增加一种直接报名资格，不引入通用规则引擎。仅新策略拒绝年级 1、4；无效年级不能默认为合格。

策略抛现有 `BusinessError`，让现有路由继续显示明确提示。但当前该异常定义在 `services.py`，该模块又导入策略，不能直接让策略导入服务。因此拟把异常移到独立 `errors.py`；保留 `from campusevent.services import BusinessError` 的兼容性。

收益：不需要在报名主流程里加入年级 if/else。代价：仍需修改数据字段、类型注册、校验、迁移与界面；不能把全系统改动说成“只加一个类”。

### 3.2 事件订阅追加邮件

保留 `MessageNotifier`，新增 `EmailNotifier`，在 `AppContainer` 中订阅。当前已经是报名写入提交后才 `publish()`，应保留这个顺序。

`MockEmailSender` 只模拟结果，收件人使用固定演示学生 ID 构成的 `student_id@campusevent.invalid`，不新增真实邮箱采集和外部服务。该选择解决“原 Student 没有邮箱字段”的需求空白，应在实现版 README 中说明。

### 3.3 防重复与失败处理

- 邮件表设置 `UNIQUE(registration_id, event_type)`。与站内消息分别存储，相同事件可以各生成一条；不能跨渠道共用一个“已经通知”的标记。
- 模拟发送不产生网络副作用。生成结果后，`record_once()` 用目标唯一键的冲突处理原子插入；不能靠先查后写或内存集合。
- 成功记录为 `SENT`，模拟故障记录为 `FAILED`，并在同一邮件事务中保存 `notification_log`。只有首次插入才新增失败日志。
- 重复发布同一事件，即使经过重启，也不新增邮件。重复失败事件不自动重试；取消后重新报名有新的报名 ID，可以收到新结果邮件。
- 邮件数据库本身不可用时，捕获并写应用错误日志；数据库恢复前不能保证数据库失败日志一定写入成功。不能让日志失败反过来影响报名结果。

不实现可靠消息队列或最终送达保证。如果进程在报名提交后、事件发布前崩溃，仍可能缺通知；应在最终报告如实列为局限。

## 4. 旧数据库升级方案

线上已经有数据，`CREATE TABLE IF NOT EXISTS` 不会自动修改旧表。

1. 实施前备份线上 SQLite，停止应用写入；未获用户进一步确认前，不操作服务器。
2. 通过数据库版本或表结构检测执行迁移，不删除数据库，不重新生成原活动或报名。
3. 为旧学生增加 `grade`。教学演示拟使用默认值 1，保证默认不获得限定资格；这不是推断真实年级。旧演示账号经明确映射可设置 S001～S004 对应 1～4，非标准账号保留默认值，不能从学号猜测。
4. 旧活动表 `policy_type` 有只允许两种类型的 CHECK 约束。需要事务化重建该表并完整复制数据和原主键；处理外键、迁移顺序和恢复设置，不能只改 Python 常量。
5. 创建邮件表及事件唯一键。旧报名不自动补发历史邮件，避免把历史初始化当成新业务事件。
6. 执行外键完整性检查、升级前后行数与关键字段对比；二次初始化不重复迁移或种子数据。任一步失败回滚。

图中展示的是应用交互，不把现有分离连接的“先校验再写入”误画成完整的并发原子事务。容量竞争和重复有效报名竞争需在实现阶段专项检查。
